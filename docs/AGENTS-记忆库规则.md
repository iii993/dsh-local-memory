# 给 agent 的记忆库使用规则（可直接复制进 AGENTS.md）

装好插件只是给了 agent 工具；它还得知道"先读 INDEX 再下钻""一个文件一个主题"这些规矩，否则会把记忆库当普通文件夹乱翻。

下面这段是这套方案配套的规则，按需删减后放进你自己的 `AGENTS.md`（或等价的项目指令文件）。

---

### 记忆库(memory)使用规则

12. **记忆库 = 本机真实文件夹里的 Markdown 文件**。工具前缀 `memory_*`，由进程内插件提供（无常驻进程）。
    **这是纯工具式记忆**：只在显式调用时读写，**不注入上下文、不做用户画像、不会在每轮对话自动塞历史** ——
    需要历史偏好时必须自己主动搜，不要假设"系统已经知道"。
    - 记忆库根 `MEMORY_ROOT`：默认 `$DSH_HOME/memory`；可用环境变量 `DSH_MEMORY_DIR` 或插件 config 的 `memoryRoot` 覆盖
    - ⭐ `memory_remember({ content, topic?, scope? })` —— **要记东西就用这个**，不要自己 `memory_write`：写入子代理先查重（避免同一主题堆出多个文件）、再决定 create/append/patch，整条作废时才 delete（**理由必填**）。返回物是客观操作记录 + 写入后盘上的**实际内容**；删除会列出理由与 `.trash/` 备份路径
    - `memory_gc({ scope?, apply? })` —— **记忆库体检/整理**（整理子代理）：找同主题多文件、过时内容、缺失 frontmatter。默认**只读**；`apply: true` 才允许动手（重建 INDEX、补 frontmatter、**合并明显重复的文件**）。删除同样必须带理由并列出备份路径
    - ⭐ `memory_recall({ intent, scope?, maxFiles? })` —— **用白板子代理做检索，返回它实际读过的文件原文**（默认前 5 个）。主 agent 每一步请求都要重发全部工具定义，而子代理只挂 2 个工具 —— 一次 recall 把 4~8 轮检索挪到主上下文之外。**这是默认检索入口**；单次约 10~30 秒。返回物由插件的**操作日志**决定（日志里读过哪些文件就返回哪些），不是子代理的总结，所以不会被润色或漏掉；超出上限的文件只列路径并报数。子代理不可用时自动回退到确定性检索并明确标注。它猜不到关键词时能读 `INDEX.md` 逐层导航、或用空 `query` 列目录（INDEX 不进返回物）
    - `memory_search({ query, scope?, content?, regex?, sort?, since?, limit? })` —— **返回文件路径 + 命中类型 + 大小 + 日期 + 一句话说明（`summary`，缺失时回退正文标题），不返回正文**，由你决定读哪一个；`query` 默认是大小写不敏感子串，命中范围 = **文件名 + `tags` + 正文**（`updated`/`source` 等元数据不计，所以搜"实测"不会全线命中）；`regex: true` 时按正则处理（等价 `gi`），例 `抓包|发包`、`断点.*放行`；**多词按分隔符（空格 / 斜杠 / 竖线 / 逗号）自动拆开 OR**：`"chrome 抓包"` = `chrome` 或 `抓包`，整串精确命中仍优先；长中文串（`"网络请求分析"`）不做拆分——那是语义判断，交给 `memory_recall` 的子代理；**`query` 传空串 = 列目录**（配 `scope`）；`sort: "updated"` 配 `since: "YYYY-MM-DD"` 就是"看看上周记了什么"。典型场景：需要**自己核对候选列表**，或 recall 的节选不够精确时
    - `memory_read({ path })` —— 传文件返回其内容；传目录返回该层 `INDEX.md`（逐层下钻入口）
    - `memory_write({ path, content, mode })` —— mode：`create`(默认) / `append`(按要点去重追加) / `replace`(整文件覆盖)；自动建目录、自动更新 INDEX 链
    - `memory_patch({ path, old, new })` —— **局部改写**：把文件里**唯一出现**的 `old` 换成 `new`。改错别字、更新某个数值用这个，比"read 全文 + replace 全文"省上下文也不容易误伤；`old` 出现 0 次或多次都会报错并说明原因
    - `memory_delete({ path, recursive? })` —— 删除并同步 INDEX；禁止删根目录、禁止单独删 `INDEX.md`
    - `memory_reindex({ scope? })` —— 从实际文件系统无损重建全部 `INDEX.md`
    - ⚠️ **`replace` / `memory_patch` / `memory_delete` 覆盖或删除前，原文件会备份到 `<MEMORY_ROOT>/.trash/`**（以 `.` 开头，不进 INDEX 也不进搜索）。它是安全网不是版本控制 —— 库不在 git 下时重要内容仍要另行备份

13. **检索协议（成本从低到高，命中即停）**：
    ① ⭐ **探索性检索（默认入口）**：`memory_recall({ intent, scope?, maxFiles? })` —— 意图用自然语言描述即可，例 `memory_recall({ intent: "找 chrome 抓包相关的做法" })`。子代理替你看 INDEX、试关键词、判断该读哪个，主上下文只增加它最终读到的内容。**不知道搜什么词、或要试几轮时最省**；
    ② **精确检索**：已经知道关键词、且需要自己看候选列表时用 `memory_search`；若有 Everything 也可限定记忆库根搜索（只搜文件名），但 `es.exe` **不支持 GUI 的 `path:` 运算符**，必须用 `in_path`（递归）/ `parent`（非递归）；
    ③ **正文检索**：`grep` 搜记忆库目录（纯子串匹配，中文任意长度都能中）；
    ④ **目录导航**：`memory_read({ path: "" })` 读根 `INDEX.md` 再逐层下钻 —— 现在很少需要，①②一般就够；
    ⑤ **读取**：只读命中的那个文件，**不要整目录读**。

14. **写入规范**：
    - ⭐ **写记忆优先用 `memory_remember`** —— 写入子代理会先查重，避免同一主题堆出多个文件；只有"要精确控制路径与内容"时才手写 `memory_write`
    - **一个文件 = 一个主题，建议 3~8 条要点**（这是控制单次读取上下文量的关键）
    - 文件名格式 `<主题>-<细分>.md`，**必须包含将来会被搜到的关键词**（文件名就是索引）
    - 顶层分类建议固定：`技能` / `电脑操作` / `环境` / `工具` / `API` / `项目` / `用户偏好`
    - 层级建议不超过 3 层（分类/子类/文件）
    - frontmatter 必填 `tags` / `updated` / `source`（取值：`实测` / `官方文档` / `用户告知` / `推断` —— **它本身就是置信度**，不再另设字段），可选 `summary`（一句话说明，会显示在上级 INDEX 的说明列）/ `related` / `importance`；`related: [路径]` 是**显式关联**（"这条依赖/补充了那条"）——tags 只是"可能相关"，related 是你断言的关系，recall 返回时会显示"引用 →"与"← 被引用"；`importance: 高|低` 缺省即"中"，**只在该条确实有高低之分时才写**；`updated` 由插件**强制设为写入当天**，不用你填；正文用中文

15. **INDEX 维护**：每个目录的 `INDEX.md` 由工具自动维护，**只列本层直接子项（不递归）**；
    新增/删除记忆时工具会自动更新从该目录一直到根的 INDEX 链；
    外部增删（git 切换、手工建文件、外部编辑器）导致索引不一致时，用 `memory_reindex` 重建。
    - 不要手工编辑 `INDEX.md` 的主体；唯一的人工可写点是它顶部的 `> 说明:` 行（重建时保留）
    - 想让某个文件在 INDEX 里显示更好的说明？写它 frontmatter 的 `summary` 字段 —— **单一数据源**

16. **三条"先检索"硬规则**：
    - **每次设计数值时，必须先 `memory_search` 搜索**该主题，查证已有的设计规则，不得凭感觉直接定数值
    - **每次查看/使用任何 API 时，必须先 `memory_search`**；若无结果，则用其他方法（文档、源码等）拿到信息后**立即写入记忆库**：
      路径 `API/<类名>.md`，要点格式 `中文名  作用   英文名(需要传入的参数)`，`tags` 里带上 `API差异` / `新版本API` / `小版本差异`
    - **老版本与新版本有差异的 API 都要先入库**，方便后续直接检索，不用每次重新摸索
